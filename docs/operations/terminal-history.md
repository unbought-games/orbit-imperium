# Bounded runtime history

The worker can retire gameplay receipts, event generations and acknowledged committed-activity delivery. `ORBIT_PRUNE_TERMINAL_HISTORY=1` on the worker enables the additional work. The default is off. The existing seven-day game-update cleanup continues on both settings. Installation of migration 0053 alone retains the command, event and activity histories.

The worker also waits until at least one hour after the installation-wide UUIDv4 cutoff before pruning any of the three new populations. For v7 commands the additional hour starts at the identity timestamp plus 900,000 ms. The seven-day terminal horizon and the deadline margin both apply. Historical rows start their seven days at migration installation. Database triggers stamp later completions and cancellations, including those made by compatible older writers. A pending input’s initial stamp grants no deletion eligibility.

## Operation

The ordinary maintenance task sleeps 60 seconds between passes. Each pass tries 128 command groups (up to 256 receipts plus 128 links) and 128 events per universe, then 128 activity acknowledgements globally. Delivery prunes at most four 1,000-publication batches with a 100 ms yield between full batches. Each batch uses one connection, its own transaction, a one-second statement timeout and a 100 ms lock timeout. SQL cancellation or worker shutdown rolls back the incomplete transaction. The next pass reevaluates eligibility. A contended runtime row skips that universe’s command batch.

Each command/event scan examines at most 512 ordered candidate identities. If a full window yields fewer than 128 eligible groups, the worker continues after the last examined key next pass. The continuation keeps the sweep’s original upper age cutoff. New arrivals cannot extend it indefinitely while earlier pins are released. A short window wraps to the beginning. A restart resets this in-memory scan position and rechecks the same durable evidence.

Partial indexes on terminal inputs order the per-universe scans by terminal wall time and identity; the delivered-activity index orders only acknowledged activity. Claim, declaration, publication and pair checks use scalar keys. Large command, event and state JSON values are outside the eligibility predicate. The scheduler continues to use the existing pending partial indexes.

Worker metrics expose `orbit_retention_eligible_groups_capped` and `orbit_retention_oldest_eligible_record_age_seconds`, labelled by universe and kind. A sample describes unlocked eligible groups in the window examined by the last committed batch. The companion gauge `orbit_retention_scan_limited` is one when the scan or deletion limit was reached; a zero eligible count in a full window can mean protected rows precede eligible work. A count at the limit is a lower bound; pairs count once. Age measures time since the oldest selected gameplay root’s terminal stamp, event terminal stamp, delivery creation or activity acknowledgement. Empty batches report zero. Skipped/failed batches preserve the previous sample. Inspect all worker replicas, existing storage-retry metrics and warning logs when interpreting a flat sample.

## Activation and rollback

1. Keep the flag absent during deployment. Record the selected API, worker, browser and bot revisions, image digests, migration checksums, database recovery point and rollback allowlist. Rehearse the populated upgrade with the deployment migration timeouts. Verify all four indexes valid. Capture pre-activation command/event counts, pending work and age, activity pending/quarantined facts, scoped lag, active claims, reconnect behavior and storage growth.
2. Acceptance owners must finish the historical activity extraction, immutable delivery/coverage dispositions, old/new meaningful play and cohort reconciliation at the **same cutoff**, and report/source cutover for every historical consumer. Include the baseline, weekly reports, D1/D7 and measurement scripts. Verify live coverage across the cutoff and retained undelivered evidence. Until accepted, keep historical command evidence and the existing `reporting.commands` report defaults.
3. Run the disposable real Accounts–Orbit–bot integration against the selected binaries and retain revisions and results. Verify every writer, including operators, native callers, official browser and bot versions. Check every permitted rollback binary enforces expiry, handles the delivery floor and interior gaps, preserves parent resolution, claim fences and existing activity/state transactions. Exclude pre-bridge and floor-unaware rollback versions. Verify database time and persisted `command_admission_cutover.legacy_until_ms` on the serving database. Wait for the cutoff plus one hour. Verify the seven-day grace on populated state.
4. After separate activation authorization, set `ORBIT_PRUNE_TERMINAL_HISTORY=1` in the worker environment and recreate the selected worker using its normal release workflow. Verify the effective setting and first committed batches. Observe reconnect below the floor, retained pending receipts, expired missing receipts, ordinary bot progress, long timers, undelivered facts, report parity and cleanup gauges. Compare arrival and retirement rates through a complete retention interval. Relation file sizes can remain steady as PostgreSQL reuses space.
5. To pause, remove the flag or set it to `0` on **every worker** and recreate/drain them. Allow in-flight transactions to finish or roll back. Verify pending work, state, reports and reconnect continue. Roll back applications only to an approved floor-aware, expiry-enforcing release. Deleted history requires coordinated recovery from a recorded backup if needed; restoring an old accepting writer would make pruned identities executable again. Measure sustained growth before RCA closure.
