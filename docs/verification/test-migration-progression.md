# Progression test migration

Base: `a119915ffaeb881a7f54d65542478f4788bd4210`. Owned scope is the progression feature and four application fixture specs. No CI selection, shared fixture, runner, global guidance or changelog changes are included.

## Boundaries implemented

- `manufacturing-order.ts` owns local validation/submission/draft lifecycle. The hook only supplies render identities and subscriptions. Quotes, balances, pending reservations and receipts remain in the coordinator store. `send` remains the authoritative admission boundary.
- `progression-inspection.ts` owns response delivery and cancellation; the hook supplies the confirmed structural context. Late success, null responses and rejection are explicitly resolved in unit tests.
- `technology-tree.tsx` separates the actual prerequisite tree from native modal mounting, allowing missing-level text to be rendered directly without mocking the tree. The dialog retains focus, close and tab behavior.
- `catalog-tile-model.ts` owns cost-inspection eligibility and body-specific affordability. Prices remain server data and affordability is derived.
- Cancellation already has a deterministic production seam: `workCancellation`, `buildingProgress`, `researchProgress`, and coordinator/projection admission. There is no second cancellation state machine. Native confirmation controls remain browser-tested.

These fixture and static-component tests do **not** prove server authorization or persistence. Existing server HTTP/database coverage remains required and unchanged.

## Replacement coverage

- **M1** — `manufacturing-order.test.ts`: “discards held validation after an inspector identity change or cleanup”, “does not let an obsolete rejection overwrite the current draft”, and “keys edits and structural validation separately from a committed draft”. Explicit promises replace edit/dismiss/reopen/subject/session races.
- **M2** — same file: “refreshes changed … without sending the old displayed order”, “rechecks spending during validation …”, and “rejects live … changes before command admission”. Fixed expected command and paid terms; stale prices never authorize a command.
- **M3** — same file: “preserves the next draft changed …”, “does not reset a draft on …”, “validates once, sends exact displayed terms and consumes a committed draft once”, and “allows quote refresh after commitment …”. Pending/uncertain/rejected results cannot produce false success; recovery and edited drafts are independent. `action-feedback-model.test.ts` retains exact submitted labels and announcement semantics.
- **D1** — `technology-details.test.ts`: each Ion Cannon, Gauss Cannon, Heavy Laser and Plasma Turret prerequisite, disabled catalog entry, and ready state renders the actual `TechnologyDetails` and `TechnologyTree` components, including the exact missing `current / required · Required` tree rows. Assertions cover native Build disabled markup, unavailable copy, exact current/required levels, inventory, fixed three-unit costs, and refusal to inspect/send a blocked order. Technology-tree opening/closing and image decoding remain in each item’s retained successful browser journey. Static markup is not credited with focus/layout/event-handler coverage.
- **A1** — `catalog-tile-model.test.ts`: all four catalog request kinds, each resource at cost minus one micro-unit and at exact cost, selected-body isolation, disabled/locked/progress suppression, stable quote context on balances, and next-level research price invalidation. `options.test.ts` additionally protects profile/session/level invalidation. One live shared-tile class/reload journey and the research completion journey remain.
- **C1** — `progression-inspection.test.ts`: “keeps confirmed eligibility when old cancellation options arrive … fresh options” explicitly delivers both orders; stale success/null/error after cleanup cannot publish. `game-projection.test.ts` retains “refunds cancellation immediately and restores the operation on rejection”, “keeps next body actions disabled after optimistic cancellation until the confirmed snapshot includes it”, and rejected/uncertain cancellation locks. `coordinator.test.ts` retains confirmed refund exactly once and command admission before persistence. One full cancellation-to-next-command browser journey remains.
- **C2** — `work-cancellation.test.ts`: both kinds at 29,999 / 30,000 / 30,001 ms and 29 hours, unknown/future timestamps, operation identity, completion and inaccessible research; exact full-unit formatting without upward rounding. Browser retains both consumers at 30,000 ms plus construction’s 29,999-to-30,000 click-time recheck, safe initial focus, Escape focus return, confirmation and rejection.
